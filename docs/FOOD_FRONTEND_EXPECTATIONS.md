# Restaurant frontend expectations

Implemented routes: `/food`, `/food/cart`, `/food/orders/[token]`, `/admin/food`, `/admin/food/settings`, `/kitchen`.

Source of truth: `docs/FOOD_API_CONTRACT.md`, `lib/food-domain.mjs`, `lib/food-service.mjs`, `lib/food-http.mjs`. Frontend uses no fallback meals, contacts, invented hours/addresses/fees or fabricated success records. Product cart remains untouched and separate.

## Explicit owner-supplied display defaults

The owner subsequently supplied Monday–Friday closing **18:00 Bangkok**, **20-minute preparation**, and pickup text **บ้าน ทุ่งประดู่**. `foodSettingsDisplay` displays these known facts only when the API has no value; actual API values take precedence. Opening time stays blank and no delivery fee is inferred. Customer ordering still requires all three backend booleans, especially `accepting_now`, so these display defaults cannot open the restaurant or replace the required tracking secret. Settings form uses the supplied close/prep/location, not made-up opening times. Incomplete hour pairs are omitted from a **closed** settings PUT because the current schema requires complete open/close pairs; known close18 remains visible until an owner supplies real openings. Blank delivery-zone fee is a validation error, never converted to 0; remove an unconfigured zone rather than silently making delivery free.


## Exact HTTP shapes consumed

- `GET /api/food/menu` → `{items: Menu[]}`. Menu fields used: `id`, `name`, `description`, `category`, `image_url`, `price`, `source_type`, `available`, `stock`, `daily_limit`, `allergens` (string), `allergens_confirmed`, `options`.
- `GET /api/food/menu?include_inactive=1` → `{items: Menu[]}` for owner/manager; soft-deleted entries are read-only.
- `POST /api/food/menu`, `PUT /api/food/menu/:id` → `{item: Menu}`. Explicit menu payload: name, description, category, image_url|null, price (baht number), source_type, available, daily_limit|null, stock, allergens, allergens_confirmed, options. Existing resale stock writes include `expected_stock` from original read. Frontend reads menu list again and locates returned item ID before showing saved state.
- Menu options: `[{id,name,min,max,choices:[{id,name,price_adjustment,available}]}]`. Select and checkbox controls respect min/max and choice availability. Cart stores `[{group_id,choice_ids:[...]}]`; no price submitted to server. UI price estimate includes configured adjustments. Unconfirmed allergens always show `สอบถามร้านเรื่องสารก่อภูมิแพ้ก่อนสั่ง`.
- Image upload: `POST /api/images` multipart FormData key `file` → `{id,url:'/api/images/<id>'}`. Frontend GETs returned image and checks image content-type before attaching it; external image URLs are not accepted.
- `GET /api/food/settings` and manager `PUT /api/food/settings` → `{settings: Settings}`. UI uses exact settings fields: timezone, weekdays, order_accepting, pickup_enabled, delivery_enabled, hours weekday keys `1`–`5` with open/close strings, pickup_address, delivery_zones `{id,name,fee,enabled}`, prep_minutes, daily_capacity, configured, **accepting_now**, online_payment_enabled.
- **Ordering fails closed unless `order_accepting === true`, `configured === true`, and `accepting_now === true`.** The backend computes accepting_now using Bangkok business hours and required tracking secret. Missing/error/loading settings never enable add or initial submit.
- Settings PUT explicitly fixes timezone `Asia/Bangkok`, weekdays `[1,2,3,4,5]` and online_payment_enabled false; no preset operating hours/address/zone is invented. Zero prep/capacity means unset while closed. Successful PUT is followed by GET for persisted settings.
- `POST /api/food/orders`: `{customer_name,phone,method,scheduled_at,address,zone_id,lines:[{menu_id,quantity,options:[{group_id,choice_ids}]}],notes,client_request_id}`. Bangkok datetime input becomes explicit `+07:00` ISO seconds. Pickup address/zone empty or null. No card or automatic slip verification.
- Submit response must have `{order:{id,...},tracking_token:string}` before success/clear/redirect. UUID generated by `crypto.randomUUID()`. Cart and guest draft persist under independent `tukshop-food-cart-v1`. Before sending, entire immutable request is persisted as pendingSubmission; network/5xx/unconfirmed responses lock edits and retry the identical body/key, including after reload or restaurant closure. Definitive 4xx except IDEMPOTENCY_CONFLICT releases editing; pending unknown result cannot be silently replaced with a fresh request. Success clears food cart and guest draft only.
- `GET /api/food/orders/:token` → `{order: PublicOrder}`. `PublicOrder.items` (not lines) has `{menu_id,name,quantity,unit_price,options:[{group_id,group_name,choice_ids,choice_names,price_adjustment}]}`. Totals/status/payment_status are server values. Pending means saved, not restaurant accepted. Rejected/cancelled are explicit terminal states. Active orders refresh every 15 seconds; tokens never looked up by sequential order ID. Tracking route has noindex/nofollow/no-referrer metadata.
- `GET /api/food/admin/orders?date=YYYY-MM-DD` → `{orders: Order[],truncated:boolean}`. No date means backend's Bangkok today. `truncated:true` explicitly warns list is incomplete. Kitchen displays number/time/method/items/options/notes, never customer contact fields; owner/manager additionally see fulfillment details and manual-payment controls.
- `PATCH /api/food/admin/orders/:id`: `{status}` or `{payment_status:'paid'}` → `{order}`; followed by GET and exact ID/state check before saved message. No optimistic state advancement. Kitchen actions pending→accepted/rejected→[terminal]; accepted→preparing→ready→completed. Manager cancellation and paid confirmation require explicit confirmation controls. No automatic payment.
- Non-2xx: `{error,code}`. Request helper preserves status/code, surfaces error, does not fabricate empty success. JSON parse/network errors also remain errors.

## Server permissions

`/admin/food/layout.jsx` server session gate requires owner/manager, legacy admin only when no explicit role. `/kitchen/page.jsx` server gate requires owner/manager/kitchen and passes manager boolean from verified session. Client permissions are not API authorization; every write and staff read still relies on backend authorization. Shared Navbar/home/footer/auth/product files are intentionally outside frontend scope.

## Verification

Node test suites use real Zustand state, SWC-compiled React components and react-test-renderer interactions. HTTP boundary mocks use exact contract shapes; backend service/HTTP/domain and SQL integration suites are separate. No build, install, migration, or commit is performed by the frontend agent. Browser/live MariaDB walkthrough remains parent integration verification.
