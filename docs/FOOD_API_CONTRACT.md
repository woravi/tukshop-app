# Restaurant API contract

All endpoints `/api/food`, JSON, Node runtime, no cache. Money fields `price`, `fee`, `price_adjustment`, `subtotal`, `delivery_fee`, `total` are baht numbers with <=2 decimal places; calculations/storage use integer satang. IDs are strings. Errors `{error: string, code: string}` with 400 INVALID_INPUT, 401 UNAUTHORIZED, 403 FORBIDDEN, 404 NOT_FOUND, 409 CLOSED / CAPACITY / UNAVAILABLE / IDEMPOTENCY_CONFLICT / INVALID_TRANSITION / EXPIRED, 429 RATE_LIMITED, 500 INTERNAL_ERROR. No online payment; new requests are unpaid and pending. Dates require ISO8601 with explicit timezone. Bangkok business calendar, Monday–Friday only.

## Menu
`GET /menu` → `{items: Menu[]}` public active (including sold-out/unavailable items); `?include_inactive=1` owner/manager only includes soft-deleted items. `POST /menu` owner/manager → 201 `{item: Menu}`. `PUT /menu/:id` owner/manager full replacement → `{item: Menu}`. `DELETE /menu/:id` owner/manager soft-deletes → `{ok:true}`.

Menu write/body and read item:
```json
{"id":"1","name":"ข้าวกะเพรา","description":"","category":"อาหารจานเดียว","image_url":null,"price":65,"source_type":"made_to_order","available":true,"daily_limit":30,"stock":0,"allergens":"","allergens_confirmed":false,"options":[{"id":"egg","name":"ไข่","min":0,"max":1,"choices":[{"id":"fried","name":"ไข่ดาว","price_adjustment":10,"available":true}]}]}
```
`id` ignored on writes. `image_url` null or existing `/api/images/<positive id>` only. `daily_limit` null means no item-specific daily limit (restaurant capacity still enforced); resale requires finite nonnegative integer `stock`. Stock updates on existing resale items must send `expected_stock` equal to previously read stock, otherwise 409 CAPACITY (prevents lost reservations). `options` groups and choice IDs unique, choice max selection one per choice, min/max integer. No freeform prices from cart. `allergens_confirmed:false` means UI must say ask restaurant, not imply allergy safety. `deleted` boolean read-only.

## Settings
`GET /settings` → `{settings: Settings}` sanitized public; same shape from owner/manager `PUT /settings` full replacement. Initial accepting false; empty hours/address/zones/capacity are intentional. `configured` and `accepting_now` read-only computed. `order_accepting` is the saved owner switch; customer UI must use `accepting_now === true` (also checks Bangkok weekday/current hours and server tracking-secret availability) to show the shop open. `online_payment_enabled` always false.
```json
{"timezone":"Asia/Bangkok","weekdays":[1,2,3,4,5],"order_accepting":false,"pickup_enabled":true,"delivery_enabled":true,"hours":{"1":{"open":"09:00","close":"17:00"},"2":{"open":"09:00","close":"17:00"},"3":{"open":"09:00","close":"17:00"},"4":{"open":"09:00","close":"17:00"},"5":{"open":"09:00","close":"17:00"}},"pickup_address":"","delivery_zones":[{"id":"nearby","name":"พื้นที่ที่ร้านยืนยัน","fee":20,"enabled":true}],"prep_minutes":30,"daily_capacity":100,"configured":false,"accepting_now":false,"online_payment_enabled":false}
```
No fabricated location or distance. To enable acceptance all five weekday hours, positive prep_minutes/daily_capacity, pickup address if pickup enabled, at least one named enabled delivery zone with fixed fee if delivery enabled are required. Enabled at least one method. Weekend requested fulfilment and weekend submissions rejected. Requests must be submitted during today's business hours; scheduled fulfilment must be within its day's hours, >= now+prep_minutes, <=7 days ahead. Capacity counts meal quantities per Bangkok fulfilment day (not orders), only accepted, preparing, ready, completed with a held reservation. Pending requests reserve neither stock nor daily capacity and do not promise fulfilment; staff acceptance checks availability atomically. Rejected/cancelled requests count no capacity.

## Operations / verification

- Apply `sql/006_food.sql`, then `sql/007_food_pending_safeguards.sql` before starting this backend. Both are repeatable. 006 creates no menu samples or images and starts closed; 007 adds pending expiry/reservation state and admission indexes. 007 converts predeploy legacy pending fixtures by returning previously reserved resale stock exactly once, retaining accepted/completed reservations and all snapshots. Stop old food writers while applying 007; do not run an old service against this schema.
- Set `FOOD_TRACKING_SECRET` to a persistent server-only random secret (at least 32 characters; generate 32 random bytes and hex-encode). Do not expose it through `NEXT_PUBLIC_*`, change it casually, or log request/tracking keys. Without it `accepting_now` is false and POST order returns 409 CLOSED.
- Backend unit/adapter/HTTP suite: `node --test tests/food-backend-domain.test.mjs tests/food-service.test.mjs tests/food-sql-store.test.mjs tests/food-http.test.mjs`.
- Opt-in real MariaDB test: provision an EMPTY disposable database whose name ends `_food_test`; provide normal `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, then run `FOOD_TEST_ALLOW_WRITES=yes node --test tests/food-mariadb.integration.mjs`. It applies 001+006+007, exercises repeatable migrations, legacy pending conversion, actual simultaneous submissions/acceptance, both source-type daily limits, rollback, admission persistence and expiry, and removes its tables. It refuses nonempty databases and never runs through `npm test`.
- SQL adapter stores DATETIME in UTC strings and reads formatted UTC explicitly, independent of host/driver timezone. Service serializes **all** food writes by locking settings row 1 first; do not bypass that lock from custom scripts. At larger throughput replace the global mutex with tested per-service-day capacity rows, not unlocked aggregate SUM checks.

## Customer order
`POST /orders` public → 201 `{order: PublicOrder, tracking_token: "<64 hex>", replayed:false}`; exact idempotent replay →200 same shape replayed true. `client_request_id` must be cryptographically random opaque 32–128 character token (hex UUID without hyphens also works; UUID string supported). Retain the same body and key until success. Tracking token deterministically keyed from the opaque random request ID via server secret `FOOD_TRACKING_SECRET` (>=32 chars), hash only stored. The secret is required to accept any orders and must remain stable across deployments. Request key must be generated with `crypto.randomUUID()` or random bytes, never phone/time/counter.
```json
{"customer_name":"ชื่อผู้รับ","phone":"0812345678","method":"pickup","scheduled_at":"2026-11-06T12:00:00+07:00","address":"","zone_id":null,"lines":[{"menu_id":"1","quantity":2,"options":[{"group_id":"egg","choice_ids":["fried"]}]}],"notes":"","client_request_id":"<random UUID>"}
```
For delivery, nonempty address and enabled zone_id required. For pickup omit address/zone_id (empty/null accepted). Phone must be a Thai domestic number beginning 0 with 9–10 digits, or its +66 equivalent (8–9 digits after country code); spaces, hyphens and parentheses are stripped and storage uses +66. This validates syntax only, not SMS or ownership. Max 30 lines, quantity 1–50, max 100 meal units; strings bounded. Unknown fields rejected where security relevant (options/prices cannot override totals). Server snapshots names/options/prices/quantities at submission. Duplicate menu lines aggregate for stock, restaurant daily capacity and `daily_limit` on BOTH resale and made-to-order at staff acceptance. A later price/options/name edit does not reprice a pending request; a removed/unavailable menu or changed fulfilment source requires a fresh request. No card/slip/payment endpoints.

**Admission / expiry (owner confirmation required before launch):** a new public submission is a pending request only, not a reservation or confirmed fulfilment. Maximum **3 new requests per normalized phone per rolling 15 minutes**, persisted in SQL under the shared write lock; accepted/rejected/cancelled requests still count in this window, so cancellation cannot bypass admission. Exact idempotent replay bypasses admission without inserting or extending expiry. Limit failure is 429 RATE_LIMITED with no phone/PII. Pending expires **20 minutes after server UTC admission** and is lazily marked cancelled with `cancellation_reason:"expired"` on create, staff list/update, and tracking reads; acceptance checks the deadline again under the lock. Expired acceptance is 409 EXPIRED and never resurrects or reserves. Accepted requests do not expire. Owner must confirm these durations/limits and that staff can review requests in time. There is no SMS verification; a per-phone limit alone is not a global anti-bot defense.

`GET /orders/:tracking_token` → `{order: PublicOrder}`. PublicOrder has `id`, `status`, `pending_expires_at` (UTC ISO or null), `cancellation_reason` ("expired" or null), `payment_status` (`unpaid`/`paid`), `method`, `scheduled_at` (UTC ISO), `subtotal`, `delivery_fee`, `total`, `items:[{menu_id,name,quantity,unit_price,options:[{group_id,group_name,choice_ids,choice_names,price_adjustment}]}]`. Never customer_name/phone/address/notes/request key/token hashes in tracking or kitchen. Invalid token or unknown token always 404. Never expose sequential-id customer lookup.

## Kitchen/admin
`GET /admin/orders?date=YYYY-MM-DD` authenticated owner/manager/kitchen → `{orders:[...]}` (Bangkok fulfilment day, default today, max 500; `truncated` boolean indicates more than 500). Base PublicOrder plus kitchen-safe `notes`. Only owner/manager receive `customer_name`, `phone`, `address`, `zone_id`. No token hashes/request keys.
`PATCH /admin/orders/:id` body `{status:"accepted"}` or `{payment_status:"paid"}` or both → `{order:...}` actor-filtered. Kitchen can pending→accepted/rejected; accepted→preparing; preparing→ready; ready→completed. Owner/manager also can cancel pending/accepted/preparing/ready. Repeating current status is safe. Terminal states cannot reopen. Only owner/manager manually confirm paid; no automatic slip confirmation. The pending→accepted transition validates and reserves under the settings-row mutex: all menu availability/source types, aggregate item limits across both source types, restaurant daily capacity, and resale stock. Failure is 409 CAPACITY/UNAVAILABLE and rolls back the entire acceptance; the pending request remains unreserved. Repeat acceptance cannot decrement twice. Reject/cancel of pending never restores nonexistent stock; cancellation of an accepted reservation restores resale stock once and clears its held reservation. Completed retains its reservation/stock decrement. Daily capacity is derived only from held unreleased reservations. Fulfilment stock reservation is snapshotted so changing menu source type cannot break release.
